# Shadow Learning Influence Cohort Technical Design

Status: implemented and validated for Task 201 on `vision/shadow-agent`

## Purpose

Task 200 proves one exact causal chain from an evaluated Shadow learning to a
later independent task. Task 201 must answer the next question:

> Does this learning repeatedly improve Yansu's prediction against what the
> user actually did?

A cohort cannot be built by counting only the strongest successful chain. It
must preserve every relevant later task, including omissions, pending results,
unknown comparisons, regressions, corrections, and integrity failures.

## Measurement Defect Found During Audit

The Task 200 release proof correctly reconstructed the stored v2 ablation, but
the v2 ablation itself was not independent enough.

`ShadowTaskEvaluationInput.Observed.Task` and `.DesiredResult` come from the
Task Episode's latest hypothesis. For a profile-primary onset ablation, that
hypothesis was created from the profile response. The v2 composite then gave:

- 40% to task-hypothesis similarity;
- 30% to onset precision and recall against that hypothesis;
- 10% to observed actions;
- 15% to the materialized user result; and
- 5% to boundary timing.

That means 70% of the stored score could reward the profile branch for agreeing
with the labels it produced. Exact provenance does not make circular evidence
independent.

Task 201 therefore begins by replacing the measurement contract. No cohort or
user-facing reliability label may consume v2 ablations.

## Independent Observed Reference

`work-pattern-ablation-v3` derives one immutable, content-hash-only observed
reference from evidence that exists independently of the model's task wording:

- raw onset activity retained on the Task Episode;
- lifecycle action evidence observed while the user worked;
- the exact selected materialized user result;
- observed evidence timestamps; and
- the immutable evidence IDs and content hashes that support the reference.

Only raw `activity_event`, `terminal_event`, `accessibility_event`, and
`browser_event` evidence may supply onset, action, or result semantics. Shadow
output, Task Episode hypotheses, Memory, Knowledge, Self, and synthesized
context are not observed-user evidence. A materialized result must be unique
and must postdate completion of the paired neutral/profile prediction. Action
evidence must also postdate the prediction and precede that selected result.

The reference excludes:

- `TaskEpisode.LatestHypothesis.TaskHypothesis`;
- `TaskEpisode.LatestHypothesis.DesiredResultHypothesis`;
- alternatives generated by either ablation branch;
- evaluator prose or aggregate scores;
- Shadow output as observed-user evidence; and
- Memory, Knowledge, or Self prose that merely restates a prediction.

The Task Episode still defines lifecycle identity and workflow linkage. It does
not provide semantic scoring labels.

## Evidence Strength

The observed reference records one evidence-strength class:

```text
action_and_result
  post-onset lifecycle actions plus a materialized user result

onset_and_result
  raw onset activity plus a materialized result, but no later action evidence

result_only
  a materialized result exists without usable activity/action semantics

insufficient
  no independently observed semantic result can support comparison
```

`result_only` and `insufficient` remain visible but cannot produce a scored
pair. Onset-only semantics are explicitly weaker because prediction-selected
evidence references may influence which raw onset events were attached to the
episode.

## v3 Branch Score

For every episode predicted by a neutral or profile response, v3 computes:

- task-to-observed-action similarity;
- desired-result-to-materialized-result similarity;
- distance from the earliest independently observed action timestamp, with raw
  onset time used only as a declared fallback;
- semantic match and confidence calibration error; and
- split count when several predictions match the same evidence reference.

The branch composite dynamically normalizes only available independent
dimensions:

```text
observed action similarity       45%
materialized result similarity  45%
observed timing                  10%
```

When lifecycle action evidence is absent, raw onset activity may fill the
action dimension but the evidence-strength class remains
`onset_and_result`. Model-generated task or desired-result hypotheses always
carry zero score weight.

The highest independently supported episode becomes the branch candidate.
No prediction is a valid zero score when the observed reference itself is
sufficient; missing observed evidence is `unknown`, not zero.

One observed task can match at most one prediction. If a branch emits several
candidate tasks, its precision is `1 / prediction count` once any candidate
matches, and that precision multiplies the independent composite. Emitting a
large list therefore cannot outperform one equally accurate prediction merely
by increasing its chance of overlap.

## Persisted v3 Evidence

The immutable ablation evaluation retains no raw observed text. Its canonical
evidence JSON records:

- policy and observed-reference versions;
- evidence-strength class;
- exact onset, action, and result evidence IDs;
- each evidence role, observed timestamp, and content hash;
- the exact append-only ledger content hash and a separate semantic-text hash;
- canonical observed-reference hash;
- separate action and result hashes;
- neutral and profile dimension metrics;
- winner and boundary errors; and
- merge scope `independent_observed_evidence`.

Read-time release and cohort derivation rebuild this object from Task Episode,
Shadow evaluation, and materialized-result evidence. The Task Episode reader is
unbounded and cutoff-aware; it does not inherit the 500-row debugger limit.
Stored scores are accepted only when the reconstructed canonical JSON and every
typed value match.

## Historical Policy Boundary

`work-pattern-ablation-v2` remains immutable history and readable in Dev Tools.
It cannot satisfy:

- Task 200 `measured_improvement` or `measured_no_lift`;
- Task 201 cohort measurement;
- Work Pattern production rollout evidence; or
- any future user-facing reliability label.

The current release proof may show that a learning was admitted to both stages,
but a v2-only later task stops at `awaiting_ablation` with an explicit
`independent_ablation_not_recorded` reason.

## Cohort Unit

One cohort is keyed by the current immutable learning revision. It also exposes
the capability key so several revisions can later be aggregated without
collapsing their provenance.

One chain is keyed by:

```text
learning revision ID + later Task Episode ID
```

The same Task Episode cannot count twice for one learning. Source Task Episodes
cannot count as later tasks. A later task is relevant only when its frozen Work
Pattern selection evidence references the exact learning, or when malformed
selection evidence prevents that determination and must be retained as an
integrity exclusion.

## Cohort Accounting

Each cohort reports:

- exact source Task Episode, Shadow run, and evaluation counts;
- relevant independent later-task count;
- onset-omitted and Shadow-omitted counts;
- awaiting-result and awaiting-ablation counts;
- scored, unknown, profile-win, neutral-win, and tie counts;
- positive and negative lift totals and mean lift;
- distinct later Task Episode count;
- exact-profile correction count and corrected-chain rate;
- integrity exclusion count and reasons; and
- every chain ID and immutable navigation target.

The backend scans complete ledgers. Snapshot summaries are unbounded by hidden
top-N selection. One response contains every cohort and every chain, with a
manifest hash for each cohort and one hash-addressed snapshot ID over the exact
read cutoff. The debugger expands that returned snapshot locally instead of
issuing a second detail query that could cross a different read boundary.

Historical Shadow evaluation input is reconstructed from the exact contained
attempt available when the comparison was persisted and Task Episode evidence
visible at the requested cohort cutoff. Evidence appended after the cutoff
cannot change a same-cutoff snapshot. Evidence appended inside a later cutoff
invalidates a stale comparison until a new immutable comparison includes it.

## Reliability Policy

Task 201 uses a user-facing reliability policy separate from production
rollout:

```text
minimum scored independent later tasks  5
minimum source Task Episodes            5
minimum profile win rate                0.60
minimum mean lift                       0.03
maximum unknown rate                    0.20
maximum corrected-chain rate            0.10
maximum integrity failures              0
```

States are:

```text
awaiting_measurement
early
reliable
insufficient_quality
integrity_error
```

Five outcomes follows the existing Yansu calibration convention: fewer than
five may be shown as progress in Dev Tools but cannot be labeled usable or
reliable. This policy does not enable production profile influence. The current
production rollout gate remains a separate, stricter decision and authority is
separate again.

## Correction Semantics

A chain is corrected only when an append-only Work Pattern correction:

- targets the chain's exact frozen profile snapshot;
- has capability scope matching the learning capability; and
- exists by the cohort read cutoff.

Corrections do not rewrite old scores. They remain explicit negative evidence
for current reliability and prevent silent promotion.

## Functional Dev Tools

The existing Work Profile debugger will expose:

- overall current-cohort counts;
- early, reliable, insufficient-quality, and integrity states;
- per-learning source diversity, measured outcomes, win rate, mean lift,
  unknown rate, correction rate, and blockers;
- functional cohort expansion or detail navigation;
- every relevant later chain with exact Task Episode and Shadow run links; and
- explicit historical-policy exclusions.

The UI is read-only. It has no approve, promote, retry, repair, replay,
materialize, rollout, permission, or execute action.

## Production Rollout Separation

The existing Work Pattern production rollout remains a distinct 20-pair gate.
It now reads the complete evaluation ledger at the debugger cutoff, ignores
historical v2 rows, and recomputes every current v3 evaluation through the same
immutable onset, contained-run, result, and observed-reference joins. Any
current malformed or non-reconstructable row increments an explicit integrity
count and fails the rollout gate closed. Cohort reliability does not activate
that gate, and the rollout gate still does not grant action authority.

## Authority and Product Boundaries

1. Cohort reads append nothing.
2. Reliability is evidence about prediction quality, not permission.
3. Reliable learning does not enter Self automatically.
4. Reliable learning does not enable production influence automatically.
5. Production influence does not grant autonomous execution.
6. User-facing promotion, rollout, and authority each need their own explicit
   policy and receipt.
7. Behavior-only evidence cannot claim user reasoning.

## Validation Completed

- Prove v3 ignores task and desired-result hypothesis wording.
- Prove changing only independently observed action/result evidence can reverse
  the winner.
- Prove v2 evaluations remain historical and cannot satisfy release or cohort
  gates.
- Prove all stored v3 hashes and scores recompute.
- Prove duplicate later episodes do not inflate a cohort.
- Prove wins, regressions, ties, unknowns, corrections, and integrity failures
  all remain visible.
- Prove the fifth independent scored outcome changes `early` to `reliable` only
  when every quality threshold passes.
- Prove debugger reads create no database rows and guessed mutation RPCs are
  rejected.
- Run focused, race, complete Wails, frontend, agent, vet, production-build,
  live Browser RPC, interaction, and visual checks.

No synthetic production evidence may be created to make the live cohort ready.
